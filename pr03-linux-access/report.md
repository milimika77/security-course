# ПР №3. Управление доступом в Linux

## 1. Пользователи и группы

В ходе выполнения работы были созданы три пользователя и две группы для моделирования небольшой организации.

| Пользователь | Группа | Роль |
|---|---|---|
| alice | developers | Администратор проекта |
| bob | developers | Разработчик |
| carol | auditors | Аудитор |

Для создания пользователей использовались команды:

sudo useradd -m -G developers -s /bin/bash alice
sudo useradd -m -G developers -s /bin/bash bob
sudo useradd -m -G auditors -s /bin/bash carol

После создания для каждого пользователя был установлен пароль с помощью команды passwd.

### Разбор записи /etc/passwd

Каждая запись в файле /etc/passwd состоит из семи полей, разделённых двоеточием:

1. Имя пользователя.
2. Указатель на пароль (обычно символ x).
3. UID — уникальный идентификатор пользователя.
4. GID — идентификатор основной группы.
5. Комментарий или описание пользователя.
6. Домашний каталог пользователя.
7. Командная оболочка по умолчанию.

### Файл /etc/shadow

Файл /etc/shadow содержит хэши паролей пользователей, информацию о сроках действия паролей и параметрах политики безопасности.

Обычные пользователи не имеют доступа к этому файлу, поскольку содержащаяся в нём информация может быть использована для подбора паролей и компрометации учётных записей.

## 2. Права доступа chmod и chown

Для выполнения работы была создана структура каталогов проекта:

/srv/project/code
/srv/project/reports
/srv/project/logs

Каталог code был назначен пользователю alice и группе developers:

sudo chown alice:developers /srv/project/code

Первоначально были установлены права:

sudo chmod 750 /srv/project/code

Символьная запись прав:

rwxr-x---

Это означает:

- владелец (alice) имеет полный доступ;
- участники группы developers могут читать содержимое и входить в каталог;
- остальные пользователи не имеют доступа.

Пользователь bob входит в группу developers, поэтому мог просматривать содержимое каталога, но не мог создавать файлы при правах 750, так как группе не было предоставлено право записи.

После изменения прав на:

sudo chmod 770 /srv/project/code

группа developers получила полный доступ к каталогу, включая создание и изменение файлов.

Пользователь carol не входит в группу developers, поэтому не смог получить доступ к каталогу.

Также был создан файл отчёта q1.txt с правами 640:

rw-r-----

В числовой форме это означает:

- владелец: чтение и запись (6);
- группа: только чтение (4);
- остальные: нет доступа (0).

## 3. Настройка ACL

Стандартная модель Linux позволяет назначать права только владельцу, группе и всем остальным пользователям.

Для предоставления доступа конкретному пользователю без изменения группы используется механизм ACL (Access Control List).

Для пользователя carol были добавлены права на чтение и выполнение каталога:

sudo setfacl -m u:carol:r-x /srv/project/code

После настройки ACL пользователь carol получил возможность просматривать содержимое каталога, не являясь участником группы developers.

Попытка создать файл по-прежнему завершалась ошибкой, поскольку право записи пользователю не выдавалось.

Преимущество ACL заключается в том, что права можно выдавать отдельным пользователям без изменения структуры групп и владельцев файлов.

После удаления ACL:

sudo setfacl -x u:carol /srv/project/code

доступ пользователя carol снова был запрещён.

## 4. sudo-политики

Для пользователей были настроены различные уровни привилегий через механизм sudo.

| Пользователь | Разрешено | Ограничение |
|---|---|---|
| alice | Все команды | Без ограничений |
| bob | apt, apt-get | Только управление пакетами |
| carol | journalctl, cat /var/log/* | Только просмотр журналов |

Такое разделение реализует принцип наименьших привилегий, согласно которому пользователь получает только те права, которые необходимы ему для выполнения своих обязанностей.

Пользователь alice выступает в роли администратора и имеет полный доступ.

Пользователь bob может устанавливать и обновлять программное обеспечение, но не имеет права выполнять административные команды общего назначения.

Пользователь carol может только просматривать журналы системы для проведения аудита и контроля.

## 5. PAM

PAM (Pluggable Authentication Modules) представляет собой систему подключаемых модулей аутентификации Linux.

Файлы конфигурации PAM расположены в каталоге /etc/pam.d и используются различными службами системы, такими как login, ssh и sudo.

Модуль pam_unix.so отвечает за проверку пароля пользователя на основе данных из файлов /etc/passwd и /etc/shadow.

Ключевое слово required означает, что успешное выполнение данного модуля является обязательным условием аутентификации. Даже если последующие модули будут выполнены успешно, ошибка required-модуля приведёт к отказу в доступе.

Политика качества паролей настраивается через модуль pam_pwquality.

Для задания минимальной длины пароля 12 символов можно использовать параметр:

minlen=12

## 7. Контрольные вопросы

### 1. Что означает запись chmod 640 и кто при этом может читать файл?

Права 640 соответствуют символьной записи rw-r-----.

Владелец файла может читать и изменять файл, участники группы могут только читать, остальные пользователи доступа не имеют.

---

### 2. Чем setuid-бит на исполняемом файле отличается от sudo? Приведите пример.

setuid позволяет программе запускаться с правами владельца файла независимо от пользователя, который её запускает.

sudo предоставляет временное повышение привилегий после проверки прав пользователя.

Пример использования setuid — программа passwd, которая позволяет обычному пользователю изменять свой пароль, хотя запись происходит в защищённый файл /etc/shadow.

---

### 3. Почему хэши паролей хранятся в /etc/shadow, а не в /etc/passwd?

Файл /etc/passwd доступен для чтения всем пользователям системы.

Если бы хэши паролей хранились в нём, злоумышленник мог бы получить их и выполнять подбор паролей.

Поэтому хэши перенесены в файл /etc/shadow, который доступен только привилегированным пользователям.

---

### 4. Что произойдёт если дать пользователю bob запись sudo bash? Почему это опасно?

Пользователь сможет запустить командную оболочку bash от имени root и получить полный административный доступ к системе.

Это фактически снимает все ограничения и делает бессмысленным ограничение списка разрешённых команд.

---

### 5. Назовите разницу между командами su и sudo с точки зрения безопасности.

Команда su выполняет полный переход под другую учётную запись и обычно требует знать пароль этой учётной записи.

Команда sudo позволяет выполнять отдельные команды с повышенными привилегиями без передачи пароля root и ведёт журнал действий пользователя.

Поэтому sudo считается более безопасным и удобным способом административного доступа.

---

### 6. Как запретить конкретному пользователю использовать sudo, не удаляя его из группы sudo?

Можно создать правило в файле sudoers, которое явно запрещает выполнение любых команд через sudo для данного пользователя.

Также можно удалить или ограничить соответствующие записи в конфигурации sudo, сохранив пользователя в группе.
