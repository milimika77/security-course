# ПР №7. AppArmor, Capabilities и Docker

## Цель работы

Изучить механизмы ограничения привилегий и изоляции процессов в Linux: Linux capabilities, AppArmor и Docker. Проверить на практике принцип наименьших привилегий и работу мандатного контроля доступа.

---

# 1. Linux Capabilities

## Разбор getcap /usr/bin/ping

Команда:

```bash
getcap /usr/bin/ping
```

Результат:

```bash
cap_net_raw=ep
```

Расшифровка:

* `cap_net_raw` — capability, разрешающая создание raw-сокетов и работу с низкоуровневыми сетевыми пакетами.
* `e` (effective) — capability активна во время выполнения процесса.
* `p` (permitted) — capability входит в разрешённый набор процесса.

---

## Capabilities в системе

Для поиска capabilities использовались команды:

```bash
getcap /usr/bin/python3* 2>/dev/null
sudo find /usr -xdev 2>/dev/null | xargs getcap 2>/dev/null
```

Были обнаружены файлы с назначенными capabilities, включая:

* ping
* mount
* umount
* некоторые системные бинарные файлы

Capabilities используются для выдачи программам только необходимых привилегий без запуска от root.

---

## Capabilities текущего процесса

Команда:

```bash
cat /proc/self/status | grep -i cap
```

Поля:

* `CapPrm` — разрешённые capabilities процесса.
* `CapEff` — активные capabilities, используемые в данный момент.
* `CapBnd` — максимальный набор capabilities, который процесс может получить.

Расшифровка выполнялась через:

```bash
capsh --decode=ЗНАЧЕНИЕ
```

У shell были активны стандартные capabilities непривилегированного пользователя.

---

## Демонстрация setcap

### До setcap

```bash
python3 /tmp/test-port.py 80
```

Привязка к порту 80 без root была запрещена.

```bash
python3 /tmp/test-port.py 8080
```

Порт 8080 открывался успешно.

---

### После setcap

Команды:

```bash
sudo setcap cap_net_bind_service=ep $PYBIN
getcap $PYBIN
```

После назначения capability Python смог открывать порт 80 без sudo.

Это безопаснее запуска через sudo, потому что:

* процесс не получает полный root-доступ;
* выдаётся только одна конкретная capability;
* уменьшается риск компрометации системы.

После проверки capability была удалена:

```bash
sudo setcap -r $PYBIN
```

---

## Флаги e, i, p

Команда:

```bash
sudo capsh --caps='cap_net_raw+eip'
```

Обозначения:

* `e` — effective;
* `i` — inheritable;
* `p` — permitted.

`ep` даёт capability только текущему процессу, а `eip` позволяет наследовать capability дочерними процессами.

# 2. AppArmor

## Количество профилей

Команда:

```bash
sudo aa-status
```

В системе были загружены профили AppArmor в режимах:

* enforce
* complain

AppArmor использует мандатный контроль доступа (MAC), ограничивая действия программ независимо от прав пользователя.

---

## Анализ профилей

Для просмотра использовались команды:

```bash
ls /etc/apparmor.d/
sudo cat /etc/apparmor.d/usr.bin.man
```

Профили содержат:

* разрешения на чтение файлов;
* запуск программ;
* доступ к устройствам;
* ограничения записи.

Синтаксис AppArmor основан на описании путей и разрешений:

* `r` — чтение;
* `w` — запись;
* `ix` — выполнение программы.

---

## Профиль pr07-reader

Был создан тестовый скрипт:

* чтение разрешённого файла;
* попытка чтения `/etc/shadow`;
* запись в `/tmp`;
* попытка записи в `/etc`.

---

## Результаты работы профиля

| Действие                      | Без профиля        | complain        | enforce   |
| ----------------------------- | ------------------ | --------------- | --------- |
| Читать /tmp/pr07-allowed.txt  | Разрешено          | Разрешено       | Разрешено |
| Читать /etc/shadow            | Разрешено          | Разрешено + лог | Запрещено |
| Писать в /tmp/pr07-output.txt | Разрешено          | Разрешено       | Разрешено |
| Писать в /etc/                | Запрещено системой | Логируется      | Запрещено |

В режиме complain AppArmor только фиксирует нарушения в журнале, но не блокирует действия.

В режиме enforce нарушения реально блокируются.

---

## Разбор строки DENIED

Пример записи:

```text
AVC apparmor="DENIED" operation="mknod" profile="/usr/local/bin/pr07-reader" name="/etc/pr07-hack.txt" pid=3037 comm="pr07-reader" requested_mask="c" denied_mask="c"
```

Разбор:

* `operation="mknod"` — попытка создать файл;
* `profile=` — профиль AppArmor;
* `name=` — путь к объекту;
* `requested_mask=` — запрошенное действие;
* `denied_mask=` — запрещённое действие;
* `comm=` — имя процесса;
* `pid=` — идентификатор процесса.

# 3. Docker — изоляция

## Сравнение хоста и контейнера

| Ресурс             | Хост                    | Контейнер                   |
| ------------------ | ----------------------- | --------------------------- |
| Процессы           | Много процессов системы | Только процессы контейнера  |
| Сетевые интерфейсы | ens33, lo, docker0      | lo, eth0                    |
| Корневая ФС        | Полная система          | Изолированная ФС контейнера |
| /etc/shadow хоста  | Доступен                | Недоступен                  |
| Монтирование       | Разрешено root          | Ограничено                  |

Контейнер использует namespaces и cgroups, создавая изолированную среду.

---

## Volumes

Была примонтирована только папка:

```bash
-v /tmp/pr07-data:/data
```

Контейнер получил доступ только к `/data`.

Файл `/tmp/pr07-secret.txt` внутри контейнера был недоступен.

Это безопаснее, чем `--privileged`, потому что:

* контейнер получает доступ только к конкретной директории;
* отсутствует полный доступ к файловой системе хоста.

---

## Capabilities контейнера

### Обычный контейнер

```text
CapEff: 00000000a80425fb
```

Docker по умолчанию оставляет только ограниченный набор capabilities.

---

### privileged-контейнер

```text
CapEff: 0000003fffffffff
```

`--privileged` выдаёт контейнеру практически все capabilities Linux.

Это опасно, потому что контейнер становится близок к root-процессу хоста и может:

* управлять устройствами;
* менять сеть;
* монтировать файловые системы;
* потенциально выйти за пределы контейнера.

---

## Демонстрация NET_RAW

В образе ubuntu:22.04 отсутствовала утилита ping, поэтому для демонстрации capabilities использовался alpine.

После добавления capability `NET_RAW` утилита ping успешно запускалась внутри контейнера.

Это демонстрирует принцип наименьших привилегий: контейнеру выдаётся только необходимая capability вместо полного набора прав root.

---

## Запуск не от root

По умолчанию контейнер запускался от root:

```bash
docker run --rm ubuntu:22.04 whoami
```

Результат:

```text
root
```

После запуска через:

```bash
docker run --rm --user 1000:1000 ubuntu:22.04 id
```

контейнер работал от непривилегированного пользователя.

Попытка установки пакетов завершалась ошибкой:

```text
Permission denied
```

Это важно для безопасности, потому что злоумышленник не сможет изменять системные файлы и устанавливать программы внутри контейнера.

# 4. Итоговое задание — nginx с ограничениями

## Запуск nginx

Контейнер запускался с минимальным набором capabilities:

```bash
docker run -d \
  --name pr07-nginx \
  --cap-drop ALL \
  --cap-add NET_BIND_SERVICE \
  --cap-add CHOWN \
  --cap-add DAC_OVERRIDE \
  --cap-add SETGID \
  --cap-add SETUID \
  -p 8080:80 \
  nginx:alpine
```

---

## Возникшие трудности

На отдельных этапах наблюдалась нестабильная работа контейнера:

* nginx мог завершаться сразу после запуска;
* HTTP-соединение иногда не устанавливалось;
* в логах контейнера появлялись ошибки недостаточности прав.

Для диагностики использовались:

```bash
docker ps -a
docker logs pr07-nginx --tail 50
```

Контейнер останавливался и запускался повторно с корректировкой capabilities.

---

## Итоговый результат

После подбора минимально необходимых capabilities nginx начал корректно работать.

Проверка:

```bash
curl http://localhost:8080 | head -5
```

Результат:

```html
<!DOCTYPE html>
<html>
<head>
<title>Welcome to nginx!</title>
```

---

## Capabilities nginx

Проверка:

```bash
docker exec pr07-nginx cat /proc/1/status | grep Cap
```

Результат:

```text
CapEff: 00000000000004c3
```

Использовались capabilities:

* `NET_BIND_SERVICE`
* `CHOWN`
* `DAC_OVERRIDE`
* `SETGID`
* `SETUID`

Они необходимы nginx для:

* открытия порта 80;
* смены пользователя процесса;
* работы с файлами и правами доступа.

# 5. Эшелонированная защита

| Слой         | Инструмент         | Что ограничивает                  |
| ------------ | ------------------ | --------------------------------- |
| DAC          | chmod/chown        | Права пользователей               |
| Capabilities | cap-drop / cap-add | Привилегии процессов              |
| MAC          | AppArmor           | Доступ программ к ресурсам        |
| Изоляция     | Docker namespaces  | Процессы, сеть и файловую систему |

---

# Выводы

В ходе работы были изучены механизмы ограничения привилегий и изоляции процессов в Linux.

Linux capabilities позволяют выдавать процессу только необходимые права без использования полного root-доступа.

AppArmor реализует мандатный контроль доступа и ограничивает действия программ даже при компрометации процесса.

Docker использует namespaces и cgroups для изоляции процессов, сети и файловой системы контейнеров.

Совместное применение DAC, capabilities, AppArmor и контейнеризации создаёт эшелонированную защиту и существенно снижает последствия возможного взлома сервиса.
