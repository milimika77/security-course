# Практическая работа №10. Системы обнаружения вторжений и защита от брутфорса

# 1. Подготовка среды

Для выполнения работы была подготовлена виртуальная машина Debian 12 Bookworm. Были установлены необходимые средства защиты и тестирования безопасности.

Проверено состояние службы SSH и определён IP-адрес виртуальной машины для проведения тестовых атак.

В ходе подготовки была выявлена проблема с установкой пакета Suricata из стандартного репозитория Debian. Причиной оказалось отсутствие необходимых компонентов репозитория. После корректировки настроек APT система обновила списки пакетов и позволила установить требуемые компоненты безопасности.

---

# 2. Настройка fail2ban

Для защиты SSH-сервиса была настроена система fail2ban.

Создана локальная конфигурация jail.local, в которой определены параметры защиты:

- сервис SSH;
- максимальное количество неудачных попыток входа;
- временной интервал анализа;
- время блокировки нарушителя;
- использование backend systemd для чтения журналов.

После настройки служба была перезапущена и переведена в активное состояние.

Проверка конфигурации показала успешную загрузку правил и корректную работу механизма мониторинга журналов аутентификации.

---

# 3. Проверка работы fail2ban

Для моделирования атаки использовалась утилита Hydra.

Была выполнена серия неудачных попыток подбора пароля к SSH-сервису. После превышения установленного порога fail2ban автоматически обнаружил подозрительную активность и добавил IP-адрес источника атаки в список заблокированных.

Для контроля работы использовались команды просмотра журналов и списка заблокированных адресов.

В результате атака была успешно обнаружена и остановлена средствами fail2ban.

---

# 4. Настройка Suricata

Для анализа сетевого трафика была настроена система обнаружения вторжений Suricata.

Было создано собственное правило обнаружения признаков SSH-брутфорса. Правило отслеживает многократные подключения к TCP-порту 22 от одного источника за ограниченный промежуток времени.

После добавления правила конфигурация Suricata была проверена на корректность и успешно загружена.

Служба была запущена в режиме IDS и начала мониторинг сетевого трафика.

---

# 5. Проверка работы Suricata

Для проверки работы системы снова использовалась утилита Hydra.

В ходе анализа выяснилось, что при выполнении атаки непосредственно с той же виртуальной машины трафик проходит через интерфейс loopback и не всегда наблюдается Suricata на внешнем сетевом интерфейсе.

Данное поведение связано с особенностями сетевого стека Linux и не является ошибкой конфигурации.

Несмотря на это, работа созданного правила была проверена средствами анализа журналов и тестирования конфигурации.

# 6. Сравнение fail2ban и Suricata

| Характеристика | fail2ban | Suricata |
|----------------|-----------|-----------|
| Тип системы | HIDS | NIDS |
| Источник данных | Системные журналы | Сетевой трафик |
| Обнаружение атак | Да | Да |
| Автоматическая блокировка | Да | Нет (по умолчанию) |
| Уровень контроля | Отдельный хост | Сегмент сети |
| Основное назначение | Защита сервисов | Мониторинг и обнаружение атак |

fail2ban работает на уровне хоста и реагирует на события, уже зафиксированные в журналах системы.

Suricata анализирует сетевой трафик в режиме реального времени и способна выявлять широкий спектр атак, однако по умолчанию ограничивается уведомлением администратора без автоматической блокировки нарушителя.

Использование обеих систем одновременно позволяет реализовать многоуровневую защиту.

# Контрольные вопросы

## 1. Чем IDS отличается от IPS? Можно ли считать fail2ban IPS?

IDS предназначена для обнаружения подозрительной активности и уведомления администратора. IPS не только обнаруживает угрозы, но и автоматически принимает меры по их блокировке.

Fail2ban формально относится к классу HIDS, поскольку анализирует журналы операционной системы. Однако по своему поведению он реализует функции IPS, так как автоматически блокирует IP-адреса нарушителей.

## 2. Почему атака на localhost не приводит к блокировке по умолчанию?

По умолчанию адреса localhost включены в список ignoreip и исключаются из механизма блокировки. Это сделано для предотвращения случайной блокировки самого администратора.

Для проверки защиты следует использовать реальный IP-адрес машины, а не адрес 127.0.0.1.

## 3. Что произойдёт при maxretry=1000 и findtime=1? Будет ли такая защита реально работать против брутфорса?

При maxretry=1000 и findtime=1 система допустит до 1000 неудачных попыток входа за одну секунду. Только после этого IP-адрес будет заблокирован.

Такая защита практически бесполезна, поскольку современные инструменты перебора способны выполнять сотни попыток в секунду. За это время злоумышленник может успеть подобрать пароль. Для эффективной защиты обычно используют значения maxretry от 3 до 5 и findtime от 300 до 600 секунд.

## 4. В чём разница между сигнатурным обнаружением и обнаружением аномалий? Какой подход использует созданное правило Suricata?

Сигнатурное обнаружение основано на поиске заранее известных шаблонов атак. Система сравнивает сетевой трафик или журналы событий с базой сигнатур и выявляет совпадения.

Обнаружение аномалий основано на анализе отклонений от нормального поведения системы. Такой подход позволяет выявлять неизвестные угрозы, но часто приводит к большему количеству ложных срабатываний.

Созданное правило Suricata использует сигнатурный подход, поскольку ищет конкретный шаблон поведения, характерный для SSH-брутфорса.

## 5. Sysadmin говорит: «У нас Suricata стоит, значит брутфорс невозможен». Прав ли он?

Нет, не прав.

По умолчанию Suricata работает как IDS и только обнаруживает подозрительную активность. Она записывает события в журналы и создаёт уведомления, но не блокирует злоумышленника автоматически.

Для предотвращения атак необходимо использовать режим IPS либо дополнительные механизмы защиты, например fail2ban или средства фильтрации трафика.

## 6. Что означает параметр threshold:type both, track by_src, count 5, seconds 60?

Данная конструкция определяет условия срабатывания правила.

Параметр track by_src указывает отслеживать события по IP-адресу источника. Параметр count 5 задаёт порог в пять событий. Параметр seconds 60 определяет временное окно продолжительностью шестьдесят секунд.

Таким образом, правило сформирует предупреждение только в том случае, если от одного IP-адреса будет зафиксировано не менее пяти событий за одну минуту.

Это позволяет уменьшить количество ложных срабатываний и реагировать только на действительно подозрительную активность.

## 7. Почему важно использовать прогрессивное увеличение времени бана (bantime.increment)?

Прогрессивное увеличение времени блокировки позволяет эффективнее противодействовать повторным атакам.

При первом нарушении злоумышленник получает короткий бан. Если после окончания блокировки он продолжает атаку, время запрета увеличивается. Каждая следующая блокировка становится более длительной.

Такой механизм снижает эффективность длительных атак перебора, уменьшает нагрузку на систему и делает повторные попытки менее выгодными для нарушителя.
