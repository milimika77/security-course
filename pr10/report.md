1.2 Регулярное выражение фильтра sshd
Фильтр sshd использует несколько регулярных выражений для обнаружения неудачных попыток входа. Одно из ключевых выражений:
plain

^%(__prefix_line)sFailed \S+ for .*? from <HOST>(?: port \d*)?(?: ssh\d*)?(: (ruser .*|(\S+ ID \S+ \(serial \d+\) CA )?\S+ %(__md5hex)s(, client user ".*", client host ".*")?))?\s*$

Это выражение ищет в логах строки вида Failed password for ... from IP, где <HOST> — это IP-адрес атакующего. Дополнительные выражения обнаруживают: Invalid user, Connection closed, Connection reset, ROOT LOGIN REFUSED и другие подозрительные события.

Примечание о bantime.increment
В методичке указаны параметры bantime.increment = true и bantime.factor = 2 для прогрессивного увеличения времени бана. Однако в версии fail2ban 1.0.2 (Debian Bookworm) эти параметры не поддерживаются. При попытке добавить их в конфигурацию fail2ban не запускается с ошибкой:
plain

Failed to access socket path: /var/run/fail2ban/fail2ban.sock. Is fail2ban running?

Поэтому в данной работе использован фиксированный bantime=1800.
Что означает bantime.increment (в теории)
Прогрессивное увеличение времени бана при повторных нарушениях:

    Первый бан: 30 минут (1800 сек)
    Второй бан: 60 минут (1800 × 2)
    Третий бан: 120 минут (60 × 2)
    И так далее

Это серьёзно отбивает желание атакующего повторять попытки, так как каждый раз ждать приходится всё дольше.

Пакет suricata отсутствует в стандартных репозиториях Debian Bookworm. Для установки потребовалось подключить репозиторий backports:

5.2 Настройка интерфейса
Интерфейс в конфигурации Suricata: ens33

5.3 Своё правило (sid 1000001)
suricata

alert tcp any any -> $HOME_NET 22 (msg:"Возможный SSH брутфорс - множество SYN на порт 22"; flow:established,to_server; threshold:type both, track by_src, count 5, seconds 60; sid:1000001; rev:1;)

alert ssh any any -> $HOME_NET 22 (msg:"SSH соединение установлено - проверка протокола"; sid:1000002; rev:1;)

Примечание о синтаксисе threshold
В первоначальном варианте из методички использовался синтаксис threshold: both, track by_src, который не поддерживается в Suricata 7.0.10. Пришлось изменить на threshold:type both, track by_src.
Примечание о расположении правил
Изначально правила были созданы в /etc/suricata/rules/local.rules, но Suricata 7.0.10 ожидает их в /var/lib/suricata/rules/. Файл был скопирован:
bash

sudo mkdir -p /var/lib/suricata/rules
sudo cp /etc/suricata/rules/local.rules /var/lib/suricata/rules/

5.6 Сработавший алерт из fast.log
Алерт в fast.log отсутствует.
Почему алерт не появился?
В ходе выполнения работы выяснилось, что Suricata, настроенная на интерфейс ens33, не захватывает SSH-трафик при атаке с того же хоста. Это связано с особенностью стека Linux: когда источник и цель находятся на одном хосте, ядро направляет трафик на локальный адрес (127.0.0.1 или 192.168.9.195) через виртуальный интерфейс lo (loopback), минуя физический интерфейс ens33.
Подтверждение:
bash

sudo timeout 10 tcpdump -i ens33 port 22 -n
# 0 packets captured

ip route get 192.168.9.195
# local 192.168.9.195 dev lo src 192.168.9.195 uid 1000

Выполнены рекомендации методички: проверен интерфейс в af-packet (ens33), выполнены команды sudo suricata --list-runmodes и sudo journalctl -u suricata | tail -30. Служба запущена без ошибок, конфигурация проходит тест.
Для корректной работы Suricata в режиме NIDS требуется, чтобы атакующий трафик проходил через наблюдаемый интерфейс, то есть атака должна вестись с другого хоста в том же сетевом сегменте.

Выводы
Что узнали

    fail2ban — эффективный инструмент для защиты конкретных сервисов (SSH) от брутфорса. Работает реактивно: анализирует логи и блокирует IP после превышения порога попыток.
    Suricata — мощная система обнаружения вторжений на сетевом уровне. Работает в реальном времени, анализируя весь трафик сегмента. По умолчанию работает в режиме IDS (только обнаружение), для блокировки требуется режим IPS.
    HIDS vs NIDS — дополняют друг друга. HIDS (fail2ban) видит изнутри хоста, NIDS (Suricata) видит сетевой трафик. Использование обоих даёт эшелонированную защиту.
    Сигнатурный анализ — Suricata использует правила (сигнатуры) для поиска известных паттернов атак. Написанное правило ищет множественные SSH-подключения с одного IP.

Что было неожиданным

    Задержка backend=systemd: fail2ban с backend systemd читает логи с задержкой, из-за чего бан срабатывает не сразу после maxretry, а позже. В методичке указан идеальный сценарий (бан после 2-3 попыток), но в реальности получилось 5-7.
    Отсутствие bantime.increment: Версия fail2ban 1.0.2 не поддерживает прогрессивное увеличение бана, хотя в методичке оно описано. Пришлось использовать фиксированный bantime.
    Проблема с Suricata и loopback: Самое неожиданное — Suricata на ens33 не видит трафик при атаке с того же хоста, потому что ядро Linux отправляет его через lo. Это фундаментальная особенность стека TCP/IP, а не ошибка конфигурации. Для лабораторной работы с одной VM это ограничение, которое требует отдельной атакующей машины.
    Изменение IP: DHCP выдал другой IP после перезагрузки, что потребовало адаптации команд.
    Расположение правил Suricata: Версия 7.0.10 ожидает правила в /var/lib/suricata/rules/, а не в /etc/suricata/rules/ как указано в методичке.
    Синтаксис threshold: В Suricata 7.0.10 требуется threshold:type both вместо threshold: both из методички.

Контрольные вопросы
1. Чем IDS принципиально отличается от IPS? Можно ли назвать fail2ban системой IPS, хотя формально это упоминается как HIDS?
IDS (Intrusion Detection System) — система обнаружения вторжений. Она только обнаруживает и сигнализирует о подозрительной активности, но не предпринимает действий по блокировке. Аналогия: сигнализация в доме, которая орёт, но сама дверь не закрывает.
IPS (Intrusion Prevention System) — система предотвращения вторжений. Она не только обнаруживает, но и принимает меры: блокирует IP, рвёт соединение, режет трафик. Аналогия: сигнализация, которая захлопывает дверь перед носом вора.
Можно ли назвать fail2ban IPS?
Формально fail2ban классифицируется как HIDS (Host-based IDS), потому что он анализирует логи хоста. Однако по поведению он работает как IPS: обнаруживает атаку и блокирует IP через iptables. То есть fail2ban — это HIDS с функциями IPS, или HIPS (Host-based IPS).
2. Почему атаковать localhost (127.0.0.1) для теста fail2ban не сработает по умолчанию? Что нужно изменить чтобы это сработало (без отключения ignoreip совсем)?
По умолчанию в jail.local указано:
ini

ignoreip = 127.0.0.1/8 ::1

Это означает, что IP-адреса из диапазона 127.0.0.0/8 (все localhost) и ::1 (IPv6 localhost) никогда не банятся. Это сделано для безопасности, чтобы случайно не заблокировать самого себя.
Как заставить работать без отключения ignoreip:
Можно добавить конкретный IP в ignoreip с исключением, но это сложно. Проще — атаковать реальный IP виртуальной машины (192.168.9.195), а не 127.0.0.1. Или создать отдельный loopback-интерфейс с другим IP (например, 127.0.0.2), который не попадает в 127.0.0.1/8 — но это нетривиально.
3. Что произойдёт если установить maxretry=1000 и findtime=1? Будет ли такая защита реально работать против брутфорса?
При maxretry=1000 и findtime=1:

    Система допустит 1000 неудачных попыток за 1 секунду
    Только после этого забанит IP

Будет ли работать? Нет. Брутфорс-инструменты (hydra, medusa) могут делать сотни попыток в секунду. За 1 секунду атакующий успеет перебрать значительную часть словаря. Защита фактически отключена — бан сработает слишком поздно, когда пароль уже может быть подобран.
Правильные значения: maxretry=3-5, findtime=300-600 секунд.
4. В чём разница между сигнатурным обнаружением и обнаружением аномалий? Какой подход использует написанное вами правило Suricata?
Сигнатурный анализ:

    Система имеет базу шаблонов (сигнатур) распространённых атак
    Сравнивает трафик/логи с этой базой
    Ищет совпадения
    Плюс: высокая точность, мало ложных срабатываний
    Минус: не обнаруживает новые, неизвестные атаки

Обнаружение аномалий:

    Система строит модель "нормального" поведения
    Сигналит, когда видит отклонение от нормы
    Плюс: может найти то, что никто не видел (zero-day)
    Минус: много ложных срабатываний

Написанное правило Suricata использует сигнатурный подход:
suricata

alert tcp any any -> $HOME_NET 22 (msg:"Возможный SSH брутфорс"; ... threshold:type both, track by_src, count 5, seconds 60; ...)

Это правило ищет известный паттерн: множественные TCP-подключения на порт 22 с одного IP за короткое время. Это классическая сигнатура брутфорса.
5. Sysadmin говорит: "у нас Suricata стоит, значит брутфорс невозможен". Прав ли он, учитывая что Suricata по умолчанию работает в режиме alert, а не block?
Нет, не прав.
Suricata по умолчанию работает в режиме IDS (Intrusion Detection System), то есть только обнаруживает и сигнализирует (alert). Она не блокирует трафик автоматически.
Для блокировки нужен режим IPS (Intrusion Prevention System), который требует:

    Специальной настройки (NFQUEUE, AF_PACKET с IPS режимом)
    Правил с действием drop или reject вместо alert
    Дополнительной конфигурации ядра и сети

То есть Suricata в режиме alert увидит брутфорс, запишет в лог, но не помешает атакующему продолжать перебор. Нужен дополнительный механизм блокировки (например, fail2ban, iptables, или Suricata в IPS-режиме).
6. Напишите своими словами что означает threshold:type both, track by_src, count 5, seconds 60 в правиле Suricata.
Разбор по частям:
Table
Параметр	Значение	Пояснение
threshold	Порог срабатывания	Не сигналить при каждом пакете, а только при накоплении
type both	Оба направления	Считать и входящие, и исходящие пакеты
track by_src	Отслеживать по источнику	Группировать события по IP-адресу отправителя
count 5	5 событий	Сработать только при 5 подходящих пакетах
seconds 60	За 60 секунд	Все 5 событий должны произойти в окне 60 секунд
Своими словами: "Поднять тревогу только если с одного и того же IP-адреса пришло 5 подходящих пакетов в течение 60 секунд. Не сигналить при каждом отдельном пакете — ждать накопления."
Это нужно, чтобы не засорять логи ложными срабатываниями при одиночных подключениях.
7. Почему важно использовать прогрессивное увеличение времени бана (bantime.increment) против настойчивых атакующих?
Проблема: Атакующий может использовать несколько IP (ботнет), менять IP через VPN/Tor, или просто ждать окончания бана и атаковать снова.
Решение — прогрессивное увеличение:

    Первый бан: 30 минут
    Второй бан (после разбана): 60 минут
    Третий бан: 120 минут
    Четвёртый бан: 240 минут
    И так далее (умножаем на factor, обычно 2)

Почему это эффективно:

    Экономия ресурсов: Не нужно держать IP забаненным вечно
    Адаптивность: Первый раз — возможно ошибка, короткий бан. Повтор — явная атака, бан дольше.
    Отпугивание: Атакующий быстро понимает, что каждый раз ждать всё дольше. Это снижает мотивацию продолжать.
    Защита от перебора: Даже если атакующий меняет IP, каждый новый IP начинает с короткого бана, но если это тот же человек — он быстро упрётся в длинные баны.

В данной работе bantime.increment не удалось использовать из-за ограничений версии fail2ban 1.0.2, но в production-окружениях этот параметр крайне рекомендуется.
